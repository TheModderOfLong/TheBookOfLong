# 条件表达式解析流程分析

> 基于 `ConditionExpressionEvaluator.Evaluate()` 及其调用的 `Tokenize`、`ParseLogicOr/And/Comparison`、`CompareValues`、`IsTruthy` 等方法，对当前（2026-05-29 修复后）的解析流程做完整梳理。

---

## 一、解析总流程

条件表达式从入口 `Evaluate(plotController, expression)` 到最终 `bool` 结果，经过 5 个步骤：

```
原始表达式
  │
  ▼
Step 0: 剥离 {{...}} 延迟求值标记（可选）
  │
  ▼
Step 1: 替换 [$查询$] → 字符串值
  │
  ▼
Step 2: 求值 [&算术&] → 数值字符串
  │
  ▼
Step 3: Tokenize（词法分析）→ Token 数组
  │
  ▼
Step 4: 递归下降求值 → bool
```

### Step 0: 剥离延迟求值标记

```csharp
if (expression.StartsWith("{{")) {
    // 找到第一个 }}，剥离外层 {{ }}
    expression = expression.Substring(2, closeIndex - 2);
}
```

- `{{}}` 在 `ResolveAllCommands` 中被保护（不预解析），在 `Evaluate` 中剥离后求值
- 用途：ChooseHero 等遍历场景，条件表达式需要在每次遍历时用实时上下文求值
- **只剥离外层第一组 `{{}}`**，不会递归剥离

### Step 1: 替换 [$查询$]

```csharp
resolved = Regex.Replace(expression, @"\[\$(.+?)\$\]", m => {
    string value = ConditionQueryHandlers.ExecuteQuery(plotController, m.Groups[1].Value);
    return value ?? "";
});
```

- 正则 `\[\$(.+?)\$\]` 非贪婪匹配，替换为查询结果字符串
- 查询失败/未知类型返回空字符串 `""`
- **外层 `[$ $]` 被移除**，只留下返回值

### Step 2: 求值 [&算术&]

```csharp
resolved = Regex.Replace(resolved, @"\[&(.+?)&\]", m => {
    double arithResult = ParseArithExpr(m.Groups[1].Value);
    return double.IsNaN(arithResult) ? "NaN" : arithResult.ToString("G");
});
```

- 正则 `\[&(.+?)&\]` 非贪婪匹配
- 算术支持 `+ - * / % ^`（`^` 右结合）
- 求值失败返回 `NaN`
- **外层 `[& &]` 被移除**，只留下数值字符串

### Step 3: Tokenize（词法分析）

```
输入: Step2 输出的字符串
输出: Token 数组
```

分词规则（优先级从上到下）：

| 优先级 | 匹配条件 | Token | 示例 |
|--------|---------|-------|------|
| 1 | 空白字符 | 跳过 | `" "` → 忽略 |
| 2 | `(` 或 `)` | 单字符 token | `"("` → `"("` |
| 3 | `[` 开头，找到 `]` | `[...]` 整体 token | `"[>=]"` → `"[>=]"` |
| 4 | 其他字符，读到 `[` `(` `)` 或空白 | 值 token | `"60"` → `"60"` |

### Step 4: 递归下降求值

文法规则（优先级从低到高）：

```
or_expr    := and_expr ([OR] and_expr)*
and_expr   := comparison ([AND] comparison)*
comparison := '(' or_expr ')' | 值 [关系运算符] 值 | 值
```

`ParseComparison` 的核心逻辑：

```
1. 如果当前 token 是 "(" → 递归解析括号内表达式
2. 读取左值 left
3. 如果 left 是运算符 token → 视为 "" op right，right 取下一个 token 或 ""
4. 如果没有更多 token → 单值布尔判断 IsTruthy(left)
5. 如果下一个 token 不是运算符 → 单值布尔判断 IsTruthy(left)
6. 否则 → 读取运算符 op 和右值 right → CompareValues(left, op, right)
```

## 二、Token 分类

### 运算符 Token

| Token | 含义 | 数值比较 | 字符串比较 |
|-------|------|---------|-----------|
| `[>]` | 大于 | `>` | `string.Compare > 0` |
| `[<]` | 小于 | `<` | `string.Compare < 0` |
| `[=]` | 等于 | `abs差 < 0.0001` | `==` |
| `[>=]` | 大于等于 | `>=` | **false** |
| `[<=]` | 小于等于 | `<=` | **false** |
| `[<>]` | 不等于 | `abs差 >= 0.0001` | `!=` |
| `[IN]` | 包含于 | — | `right.Contains(left)` |

### 逻辑运算符 Token

| Token | 含义 |
|-------|------|
| `[AND]` | 逻辑与 |
| `[OR]` | 逻辑或 |

### 特殊 Token

| Token | 含义 |
|-------|------|
| `(` | 左括号 |
| `)` | 右括号 |

## 三、各类表达式解析示例

### 3.1 基本比较表达式

| 原始表达式 | Step1 后 | Step2 后 | Tokens | 求值 |
|-----------|---------|---------|--------|------|
| `[$HeroData:Favor:小白$][>=]50` | `60[>=]50` | `60[>=]50` | `["60","[>=]","50"]` | `60>=50` → **True** |
| `[$HaveLover:小白$][=]1` | `0[=]1` | `0[=]1` | `["0","[=]","1"]` | `0==1` → **False** |
| `[$HeroData:isFemale$]` | `1` | `1` | `["1"]` | IsTruthy("1") → **True** |
| `0` | `0` | `0` | `["0"]` | IsTruthy("0") → **False** |

### 3.2 算术嵌套

| 原始表达式 | Step1 后 | Step2 后 | Tokens | 求值 |
|-----------|---------|---------|--------|------|
| `[&1+2*3&][>]5` | `[&1+2*3&][>]5` | `7[>]5` | `["7","[>]","5"]` | **True** |
| `[$HeroData:Favor:小白$][>=][&10+20&]` | `60[>=][&10+20&]` | `60[>=]30` | `["60","[>=]","30"]` | **True** |

### 3.3 逻辑组合

| 原始表达式 | Tokens | 求值 |
|-----------|--------|------|
| `1[=]1[AND]2[=]2` | `["1","[=]","1","[AND]","2","[=]","2"]` | True AND True → **True** |
| `1[=]1[OR]0[=]1` | `["1","[=]","1","[OR]","0","[=]","1"]` | True OR False → **True** |
| `1[=]0[AND]2[=]2` | `["1","[=]","0","[AND]","2","[=]","2"]` | False AND True → **False** |

### 3.4 括号嵌套

| 原始表达式 | Tokens | 求值 |
|-----------|--------|------|
| `(1[=]0)[OR](2[=]2)` | `["(","1","[=]","0",")","[OR]","(","2","[=]","2",")"]` | False OR True → **True** |

### 3.5 独立运算符（左值缺失）

| 原始表达式 | Tokens | 等价语义 | 求值 |
|-----------|--------|---------|------|
| `[<]` | `["[<]"]` | `"" < ""` | **False** |
| `[=]` | `["[=]"]` | `"" == ""` | **True** |
| `[IN]` | `["[IN]"]` | `"".Contains("")` | **True** |
| `[>]` | `["[>]"]` | `"" > ""` | **False** |
| `[>=]` | `["[>=]"]` | 字符串 `>=` → **False** |
| `[<=]` | `["[<=]"]` | 字符串 `<=` → **False** |
| `[<>]` | `["[<>]"]` | `"" != ""` → **False** |
| `[=]ABC` | `["[=]","ABC"]` | `"" == "ABC"` | **False** |
| `[<]5` | `["[<]","5"]` | `0 < 5`（数值比较） | **True** |

### 3.6 延迟求值

| 原始表达式 | Step0 后 | 说明 |
|-----------|---------|------|
| `{{[$HeroData:Favor:小白$][>=]50}}` | `[$HeroData:Favor:小白$][>=]50` | 剥离 `{{}}` 后正常求值 |
| `{{$HaveLover:player$}}` | `[$HaveLover:player$]` | 遍历场景中每次用实时状态求值 |

## 四、IsTruthy 判定规则

```
空字符串/null   → False
数值 0          → False
非零数值        → True
非空非数字字符串 → True
```

## 五、CompareValues 判定规则

### 数值比较（两侧都能 `double.TryParse` 时）

- `[>]` `[<]` `[>=]` `[<=]` 直接数值比较
- `[=]` 使用容差 `abs(leftNum - rightNum) < 0.0001`
- `[<>]` 使用容差 `abs(leftNum - rightNum) >= 0.0001`

### 字符串比较（任一侧无法解析为数值时）

- `[=]` → 精确相等 `==`
- `[<>]` → 精确不等 `!=`
- `[>]` → `string.Compare > 0`（序数比较）
- `[<]` → `string.Compare < 0`（序数比较）
- `[>=]` → **False**（字符串无法合理判断大小，安全返回 false）
- `[<=]` → **False**（同上）
- `[IN]` → `right.Contains(left)`

## 六、风险点评估

### ⚠️ 风险1: NaN 值的传播

**场景**: `[&1/0&][>]5` → Step2 产生 `NaN` → `NaN[>]5`

- `double.TryParse("NaN")` 在大多数区域设置下返回 `true`，值为 `double.NaN`
- `NaN > 5` → **False**（C# 中 NaN 与任何数的比较都为 false）
- `[=]` 比较: `Math.Abs(NaN - 5) < 0.0001` → **False**（`Math.Abs(NaN)` = `NaN`）
- **结论**: NaN 相关比较全部返回 False，不会误判为 True ✅

### ⚠️ 风险2: 空值查询结果的误判

**场景**: 查询返回空字符串，如 `[$Unknown:xxx$]` → `""`

- `""[=]""` → **True** — 空串等于空串
- `""[>]""` → **False**
- `IsTruthy("")` → **False** — 独立空值为假

- **风险**: 若查询意图获取数值但返回空串（查询失败），`""[=]""` 会为 True
- **缓解**: 查询失败时 `ExecuteQuery` 返回空串，而用户正常不会写 `[$xxx$][=]` 这种无右值的表达式；如果写了，空串等于空串在语义上也是合理的

### ⚠️ 风险3: 数值精度与容差

**场景**: `0.1+0.2` 在浮点数中 ≠ `0.3`

- `[&0.1+0.2&][=]0.3` → `0.300000000000004[=]0.3` → `abs差 ≈ 4e-16 < 0.0001` → **True** ✅
- 但若两值差在 `0.0001` 附近（如 `1.00009[=]1.0`），可能产生边界争议
- **影响**: 低，游戏中很少出现这种精度边界

### ⚠️ 风险4: Tokenize 中 `[` 的贪婪匹配

**场景**: 表达式中出现非运算符的 `[xxx]` 模式

- Tokenize 遇到 `[` 就寻找 `]`，将中间内容整体作为一个 token
- 如果查询替换/算术求值后仍有 `[xxx]` 残留（正常不应出现），会被当作单个 token
- 例如 `[&1/0&]` → Step2 替换后为 `NaN`，不含 `[]`，无此问题
- **风险**: 仅在 `[` 后无配对 `]` 时，`[xxx` 会被当作值 token 读到空白/括号截止，可能产生意外拆分
- **影响**: 极低，正常流程不会产生不配对的 `[]`

### ⚠️ 风险5: Step1 查询替换后值中含 `[` 或 `]`

**场景**: 查询返回值包含方括号，如角色名 `"小[白]"`

- Step1 后: `小[白][=]1` → Tokenize: `["小","[白]","[=]","1"]`
- `[白]` 被当作一个 token，原意 `"小[白]"` 被拆散
- 左值变成 `"小"`，运算符变成 `"[白]"`（非已知运算符），走 IsTruthy("小") → **True**
- **影响**: 中等。查询返回含 `[]` 的字符串时表达式解析会出错
- **缓解**: 游戏中角色名/物品名通常不含方括号；`ExecuteQuery` 对数值查询返回纯数字字符串，不受影响；字符串查询（如 `Name`）可能包含颜色标签但不会含 `[]`

### ⚠️ 风险6: `[AND]`/`[OR]` 作为左值

**场景**: 表达式以 `[AND]` 或 `[OR]` 开头，如 `[AND]1[=]1`

- Tokenize: `["[AND]","1","[=]","1"]`
- `ParseComparison` 读取左值 `"[AND]"`，它不是 `IsOperatorToken` 识别的运算符，也不是值
- 进入 `pos >= tokens.Length` 检查 → False（还有更多 token）
- `tokens[pos]` = `"[=]"` 是运算符 → 进入比较: `CompareValues("[AND]", "[=]", "1")`
- `"[AND]"` 无法解析为数值，走字符串比较: `"[AND]" == "1"` → **False**
- **结论**: `[AND]`/`[OR]` 作为左值时，IsTruthy 未被调用，而是被当作字符串值参与比较，结果为 False
- **影响**: 低。语法错误的表达式，返回 False 是安全的行为

### ⚠️ 风险7: 多余的右值被忽略

**场景**: `1[=]2[=]3`

- ParseComparison 读取 `left="1"`, `op="[=]"`, `right="2"` → `1==2` → False
- `"[=]3"` 中的 `"[=]"` 和 `"3"` 作为剩余 token 不会被消费
- ParseLogicAnd/Or 会尝试继续匹配 `[AND]/[OR]`，不匹配则停止
- **结论**: 多余部分被静默忽略，不会报错
- **影响**: 低。语法错误的表达式，但不会崩溃；可在 Step4 后检查 `pos == tokens.Length` 来检测未消费的 token

### ⚠️ 风险8: `[IN]` 的操作数顺序

**场景**: `A[IN]B` 意味着 `B.Contains(A)`

- `CompareValues` 中: `case "[IN]": return right.Contains(left);`
- 即左值是被搜索的子串，右值是被搜索的容器
- **与直觉可能相反**: 通常 `A IN B` 意味着 "A 在 B 中"，代码实现的正是这个语义
- **影响**: 无，语义正确

### ⚠️ 风险9: `{{}}` 延迟标记只处理外层第一组

**场景**: `{{$xxx$}}{{$yyy$}}`

- Step0 只剥离从 `{{` 到第一个 `}}` 的内容
- `{{$xxx$}}` → `$xxx$`（剥离后），`{{$yyy$}}` 残留
- **影响**: 低。延迟求值设计上就是整个表达式用一个 `{{}}` 包裹，不应出现多组

### ⚠️ 风险10: 数值比较与字符串比较的隐式切换

**场景**: `[$GetIntVal:count$][=]3` — 查询返回 `"3"`

- 两端都是数字字符串 → `double.TryParse` 成功 → **数值比较**（容差 0.0001）
- **OK**: `3 == 3` → True ✅

**场景**: `[$GetStrVal:name$][=]小白` — 查询返回 `"小白"`

- `"小白"` 无法解析为 double → **字符串比较** → 精确相等
- **OK**: `"小白" == "小白"` → True ✅

**场景**: `3.0[=]3` — 两端都是数值

- `double.TryParse` 成功 → 数值比较 → `abs(3.0-3) < 0.0001` → True ✅

**场景**: `"01"[=]1` — 两侧都能解析为数值

- 数值比较: `1 == 1` → True
- 如果期望字符串精确比较 `"01" != "1"`，则会不符预期
- **影响**: 低。条件表达式中的值几乎都来自查询返回的数值或字面量，不会出现 `"01"` vs `1` 的场景

## 七、风险汇总

| 编号 | 风险 | 严重性 | 当前状态 | 建议 |
|------|------|--------|---------|------|
| 1 | NaN 值传播 | 低 | ✅ 安全 | NaN 比较全为 False，无误判风险 |
| 2 | 空值查询误判 | 低 | ✅ 可接受 | `""[=]""` 为 True 语义合理 |
| 3 | 数值精度容差 | 低 | ✅ 安全 | 0.0001 容差覆盖绝大多数场景 |
| 4 | `[` 无配对 `]` | 低 | ✅ 安全 | 正常流程不产生 |
| 5 | 查询值含 `[]` | **中** | ⚠️ 潜在问题 | 游戏数据通常不含方括号，实际触发概率低 |
| 6 | `[AND]/[OR]` 作左值 | 低 | ✅ 安全 | 语法错误返回 False |
| 7 | 多余右值被忽略 | 低 | ⚠️ 可改进 | 可加 pos 检查并输出 Warning |
| 8 | `[IN]` 操作数顺序 | 无 | ✅ 正确 | 语义符合直觉 |
| 9 | `{{}}` 多组 | 低 | ✅ 安全 | 设计上不允许多组 |
| 10 | 数值/字符串隐式切换 | 低 | ✅ 可接受 | 条件表达式中不会出现 `"01"` vs `1` |

**总体评估**: 当前解析逻辑在正常使用场景下安全可靠。唯一的中等风险（查询值含方括号）在实际游戏数据中几乎不会触发。如需进一步加固，可考虑：
1. 在 Step4 求值后检查 `pos == tokens.Length`，未消费完时输出 Warning
2. 在 Tokenize 或 ParseComparison 中对无法识别的 `[xxx]` token 输出 Warning
