# `{{}}` 双层花括号解析流程分析

## 1. `{{}}` 的设计意图

`{{...}}` 是一种**延迟求值保护机制**，在 `ResolveAllCommands` 阶段保护其内部内容不被 `[$查询$]` 和 `[&算术&]` 解析，等到下游处理器实际需要时再求值。

典型使用场景：`CheckConditionCallFuc` 的回调参数中包含查询指令，这些指令应在条件判断后的分支执行时才求值，而非在 `ResolveAllCommands` 阶段就求值。

## 2. 涉及 `{{}}` 的三个阶段

| 阶段 | 方法 | 对 `{{}}` 的处理 |
|------|------|-----------------|
| A. 查询指令解析 | `ResolveAllCommands` | 保护 `{{}}` 内部不被解析 |
| B. 参数分割 | `ParseCommandParams` → `SplitRespectingBraces` | 跳过 `{{}}` 内的 `#` 分隔符 |
| C. 花括号剥离 | `ParseCommandParams` → `StripBraces` | 剥离外层 `{{}}` |

## 3. 完整追踪示例

### 输入

`clickCallFuc` 值为：
```
SpePlotFuc;SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=SUBARG$]}}|SpePlotFuc;CheckConditionCallFuc*[$GetStrVal:角色结缘返回函数$][=][$null$]#SpePlotFuc#{{SetStringValue*角色结缘返回参数#[$null$]}}
```

假设 `SUBARG` 当前值为 `"红宝石"`。

---

### 阶段 A：`ChangeNextPlotQueryResolvePatch.Prefix` → `ResolveAllCommands`

#### Step 0: SUBARG 替换

`input.Contains("SUBARG")` → `true`

**⚠️ SUBARG 替换在 `{{}}` 保护之前执行**，`{{}}` 内的 SUBARG 也会被替换。

```
替换前: ...SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=SUBARG$]}}|...
替换后: ...SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=红宝石$]}}|...
```

#### Step 1: 保护 `{{...}}`

正则 `\{\{(.+?)\}\}`（**懒惰匹配**）：

| # | 匹配内容 | 占位符 |
|---|---------|--------|
| 0 | `{{[$GlobalData:GenerateRareLvColorText=红宝石$]}}` | `__PROTECT_0__` |
| 1 | `{{SetStringValue*角色结缘返回参数#[$null$]}}` | `__PROTECT_1__` |

替换后：
```
SpePlotFuc;SetStringValue*TEMP#__PROTECT_0__|SpePlotFuc;CheckConditionCallFuc*[$GetStrVal:角色结缘返回函数$][=][$null$]#SpePlotFuc#__PROTECT_1__
```

#### Step 2: 解析 `[$...$]`

`__PROTECT_0__` 和 `__PROTECT_1__` 内的查询已被保护，不会被解析。

外部匹配：
- `[$GetStrVal:角色结缘返回函数$]` → 假设返回 `"CheckConditionCallFuc"`
- `[$null$]` → 返回 `""`

替换后：
```
SpePlotFuc;SetStringValue*TEMP#__PROTECT_0__|SpePlotFuc;CheckConditionCallFuc*CheckConditionCallFuc[=]#SpePlotFuc#__PROTECT_1__
```

#### Step 3: 无 `[&...&]`，跳过

#### Step 4: 还原保护区域

```
SpePlotFuc;SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=红宝石$]}}|SpePlotFuc;CheckConditionCallFuc*CheckConditionCallFuc[=]#SpePlotFuc#{{SetStringValue*角色结缘返回参数#[$null$]}}
```

#### Step 5: Postfix 恢复

`ChangeNextPlotQueryResolvePatch.Postfix` 将 `firstPlot.clickCallFuc` 恢复为原始值。

---

### 阶段 B：`ChangeNextPlot` 的 `|`/`;` 分割 + `SendMessage`

原 `ChangeNextPlot` 用 `|` 分割多回调，用 `;` 分割方法名和参数：

**`|` 分割**：
1. `SpePlotFuc;SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=红宝石$]}}`
2. `SpePlotFuc;CheckConditionCallFuc*CheckConditionCallFuc[=]#SpePlotFuc#{{SetStringValue*角色结缘返回参数#[$null$]}}`

**`;` 分割** → `SendMessage`：
1. `SendMessage("SpePlotFuc", "SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=红宝石$]}}")`
2. `SendMessage("SpePlotFuc", "CheckConditionCallFuc*CheckConditionCallFuc[=]#SpePlotFuc#{{SetStringValue*角色结缘返回参数#[$null$]}}")`

---

### 阶段 C：`SpePlotFucPrefix` 处理

以第 2 个回调为例，`param` 为：
```
CheckConditionCallFuc*CheckConditionCallFuc[=]#SpePlotFuc#{{SetStringValue*角色结缘返回参数#[$null$]}}
```

#### C1: `ResolveAllCommands` 二次解析

`SpePlotFucPrefix` 第 70 行再次调用 `ResolveAllCommands`：
- **Step 0**: 无 `SUBARG`，跳过
- **Step 1**: 保护 `{{SetStringValue*角色结缘返回参数#[$null$]}}` → `__PROTECT_0__`
- **Step 2**: 无外部 `[$...$]`（`CheckConditionCallFuc[=]` 不是查询语法）
- **Step 3**: 无 `[&...&]`
- **Step 4**: 还原 → 与输入相同

**`param` 不变**。

#### C2: `ParseCommandParams` 解析

`param = "CheckConditionCallFuc*CheckConditionCallFuc[=]#SpePlotFuc#{{SetStringValue*角色结缘返回参数#[$null$]}}"`

1. **按 `*` 分隔指令名和参数**：
   - `fucName = "CheckConditionCallFuc"`
   - `paramPart = "CheckConditionCallFuc[=]#SpePlotFuc#{{SetStringValue*角色结缘返回参数#[$null$]}}"`

2. **`SplitRespectingBraces` 按 `#` 分隔**（跳过 `{{}}` 内的 `#`）：

   逐字符扫描：
   ```
   C h e c k C o n d i t i o n C a l l F u c [ = ] # S p e P l o t F u c # { { S e t S t r i n g V a l u e * 角色 结缘 返回参数 # [ $ n u l l $ ] } }
   ↑ 深度=0的#                      ↑ 深度=0的#      ↑depth++ ↑                      ↑depth内  ↑depth--
   ```

   结果：
   - `fucParams[0] = "CheckConditionCallFuc[=]"`
   - `fucParams[1] = "SpePlotFuc"`
   - `fucParams[2] = "{{SetStringValue*角色结缘返回参数#[$null$]}}"`（内部的 `#` 被保护）

3. **`StripBraces` 剥离外层 `{{}}`**：
   - `fucParams[0] = "CheckConditionCallFuc[=]"` → 无 `{{}}`，不变
   - `fucParams[1] = "SpePlotFuc"` → 无 `{{}}`，不变
   - `fucParams[2] = "{{SetStringValue*角色结缘返回参数#[$null$]}}"` → `"SetStringValue*角色结缘返回参数#[$null$]"`

   **最终 fucParams**：
   ```
   [0] = "CheckConditionCallFuc[=]"
   [1] = "SpePlotFuc"
   [2] = "SetStringValue*角色结缘返回参数#[$null$]"
   ```

#### C3: `TryCallFucCheckConditionCallFuc` 执行

- `expression = fucParams[0] = "CheckConditionCallFuc[=]"`
- `ConditionExpressionEvaluator.Evaluate` → tokenize 得 `["CheckConditionCallFuc", "[=]"]`
  - `IsOperatorToken("[=]")` → `true`
  - `opRight = "CheckConditionCallFuc"`
  - `CompareValues("", "[=]", "CheckConditionCallFuc")` → `"" == "CheckConditionCallFuc"` → **False**
- `result = False`
- `callFucName = fucParams[3]`... 但 `fucParams.Length = 3`，无 False 分支
- 不执行任何回调

> **⚠️ 这里有一个问题**：`StripBraces` 在 `ParseCommandParams` 中统一剥离了 `{{}}`，但 `CheckConditionCallFuc` 的参数布局是 `条件#TrueCallFucName#TrueCallFucParam#FalseCallFucName#FalseCallFucParam`。原意图是 `fucParams[2]` 作为 `TrueCallFucParam`，但由于 `{{}}` 已被剥离，内部的 `#` 未被保护，导致 `SplitRespectingBraces` 时 `fucParams[2]` 被正确保护。然而 `StripBraces` 剥离了 `{{}}` 后，`fucParams[2]` 变成了 `"SetStringValue*角色结缘返回参数#[$null$]"`——这个值中的 `#` 不再受保护，如果后续有基于 `#` 的二次分割，就会出问题。

## 4. `SplitRespectingBraces` + `StripBraces` 的协作机制

```
原始 paramPart: A#B#{{C#D}}#E
                           ↓ SplitRespectingBraces(按 # 分隔)
               ["A", "B", "{{C#D}}", "E"]
                           ↓ StripBraces(逐项剥离 {{}})
               ["A", "B", "C#D", "E"]
```

**设计意图**：`{{}}` 的作用是保护内部的 `#` 不被参数分割拆开，分割完成后剥离 `{{}}` 让 handler 拿到干净的内容。

## 5. 各类情况分析

### 5.1 `{{}}` 内含 `#` — 正常工作

```
输入: Func*P1#{{P2a#P2b}}#P3
Split: ["P1", "{{P2a#P2b}}", "P3"]
Strip: ["P1", "P2a#P2b", "P3"]
```
`P2a#P2b` 作为一个整体参数传递给 handler，**符合预期**。

### 5.2 `{{}}` 内含 `[$...$]` — 两层保护叠加

在 `ResolveAllCommands` 中，`{{}}` 内的 `[$...$]` 被保护不解析。`StripBraces` 剥离 `{{}}` 后，handler 拿到的参数中仍包含 `[$...$]` 原文。

**问题**：handler 收到 `SetStringValue*角色结缘返回参数#[$null$]` 时，其中的 `[$null$]` 是原始文本而非解析后的值。如果 handler 直接将此值作为参数使用（如 `SetStringValue` 把它存为值），存储的就是字面量 `[$null$]`。

**是否需要二次解析**取决于 handler 的行为：
- 如果 handler 会通过 `SendMessage` 再次触发 `SpePlotFucPrefix`（如 `CheckConditionCallFuc` → `SendMessage("SpePlotFuc", param)`），则二次进入 `SpePlotFucPrefix` 时会再次调用 `ResolveAllCommands`，此时 `[$null$]` 会被正确解析
- 如果 handler 直接使用参数值（如 `SetStringValue` 直接存储），则 `[$null$]` 不会被解析

### 5.3 `{{}}` 内含 `*` — 无特殊处理

```
输入: Func*P1#{{P2a*P2b}}#P3
Split: ["P1", "{{P2a*P2b}}", "P3"]
Strip: ["P1", "P2a*P2b", "P3"]
```

`*` 在 `SplitRespectingBraces` 中不是分隔符，所以 `{{}}` 对 `*` 没有额外保护意义。但 `StripBraces` 仍会正确剥离 `{{}}`。

### 5.4 嵌套 `{{}}` — 不支持

```
输入: Func*{{外层{{内层}}外层}}
SplitRespectingBraces 扫描:
  depth: 0 → 遇到{{ → depth=1 → 遇到{{ → depth=2 → 遇到}} → depth=1 → 遇到}} → depth=0
```

`SplitRespectingBraces` 使用深度计数器，能正确处理嵌套 `{{}}` 的深度。

但 `StripBraces` 只检查 `StartsWith("{{") && EndsWith("}}")`，对于嵌套情况：
```
输入: "{{外层{{内层}}外层}}"
StripBraces: 检测到以 {{ 开头、}} 结尾且长度>4 → 剥离为 "外层{{内层}}外层"
```
内层的 `{{}}` 被保留，后续若再传给 handler 可能产生语义歧义。

### 5.5 多个独立的 `{{}}` 块 — 安全

```
输入: Func*{{A#B}}#{{C#D}}#E
Split: ["{{A#B}}", "{{C#D}}", "E"]
Strip: ["A#B", "C#D", "E"]
```
每个块独立处理，互不干扰。

### 5.6 `{{}}` 跨 `|` 分隔符 — 无法保护

`ChangeNextPlot` 用 `|` 分割多回调是在 `ResolveAllCommands` 之后、`SpePlotFucPrefix` 之前执行的。`SplitRespectingBraces` 不处理 `|`（那是 `ChangeNextPlot` 的职责）。如果 `{{}}` 跨越 `|`：

```
输入: SpePlotFuc;A#{{B|C}}#D
ChangeNextPlot 的 | 分割: ["SpePlotFuc;A#{{B", "C}}#D"]
```

`|` 分割不识别 `{{}}`，会导致拆分错误。实际使用中不应出现这种写法。

### 5.7 空 `{{}}` — 不会被 StripBraces 处理

```
输入: {{}}
StripBraces: input.Length=4, 不满足 Length>4, 不剥离
```

但 `ResolveAllCommands` 的正则 `\{\{(.+?)\}\}` 中 `.+?` 要求至少1个字符，`{{}}` 不会被保护。因此空 `{{}}` 原样传递。

### 5.8 不匹配的 `{{}}`

```
输入: Func*{{ABC#D
SplitRespectingBraces: depth=1 始终未归零，#在depth>0时不分割
结果: ["{{ABC#D"]  → 整体作为一个参数
StripBraces: 不以 }} 结尾，不剥离
结果: "{{ABC#D"
```

不会崩溃，但 `{{` 前缀被保留，语义可能不符合预期。

## 6. `ResolveAllCommands` vs `ParseCommandParams` 的 `{{}}` 处理对比

| 维度 | `ResolveAllCommands` | `ParseCommandParams` |
|------|---------------------|---------------------|
| 作用阶段 | 参数解析前 | 参数分割时 |
| 保护对象 | `[$查询$]`、`[&算术&]` 不被解析 | `#` 分隔符不被拆分 |
| 实现方式 | 正则替换为占位符 → 解析 → 还原 | 深度计数器跳过 `{{}}` 内的 `#` |
| 剥离时机 | 不剥离（还原原样） | `StripBraces` 统一剥离 |
| 嵌套支持 | 不支持（正则懒惰匹配） | 部分支持（深度计数器） |

## 7. 风险评估

| # | 场景 | 风险等级 | 说明 |
|---|------|---------|------|
| 1 | `{{}}` 内的 `[$...$]` 在 `ResolveAllCommands` 阶段不解析 | **需关注** | `StripBraces` 剥离后，handler 拿到的是含 `[$...$]` 原文的参数。若 handler 通过 `SendMessage("SpePlotFuc", ...)` 触发二次解析则安全；若直接使用参数值则 `[$...$]` 不会被解析 |
| 2 | SUBARG 在 `{{}}` 内仍被替换 | 低 | Step 0 在 Step 1 之前执行，`{{}}` 无法保护 SUBARG。当前示例中恰为期望行为，但语义不一致 |
| 3 | 嵌套 `{{}}` | 低 | `SplitRespectingBraces` 深度计数器能处理，但 `StripBraces` 只剥外层，内层保留可能产生歧义 |
| 4 | `{{}}` 跨 `\|` 分隔 | 低 | `ChangeNextPlot` 的 `\|` 分割不识别 `{{}}`，实际使用中应避免 |
| 5 | 不匹配的 `{{}}` | 低 | 不会崩溃，但 `{{` 或 `}}` 前缀被保留 |
| 6 | 空 `{{}}` | 极低 | 正则不匹配，`StripBraces` 也不处理，原样传递 |
| 7 | `StripBraces` 后内部 `#` 失去保护 | **需关注** | 剥离后参数如 `"A#B"` 中的 `#` 不再受保护。若 handler 对该参数做 `Split('#')` 二次分割则正常；若作为整体值使用则可能产生语义问题 |
| 8 | `__PROTECT_X__` 占位符碰撞 | 极低 | 正常文本不会包含此格式 |
| 9 | `CheckConditionCallFuc` 的回调参数通过 `SendMessage` 触发 | **安全** | `SendMessage("SpePlotFuc", param)` 会二次进入 `SpePlotFucPrefix`，调用 `ResolveAllCommands` 解析 `[$...$]`，再 `ParseCommandParams` 分割参数 |

## 9. 关键发现与建议

### 发现 1：`SetStringValue` 场景下 `{{}}` 内的查询指令不会被解析

`callback[0]` 的 `SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=红宝石$]}}` 经 `StripBraces` 后，value 变为 `"[$GlobalData:GenerateRareLvColorText=红宝石$]"`（字面量），`SetStringValue` 直接存储此值而不会再次调用 `ResolveAllCommands`。

**如果期望存储的是查询结果而非查询表达式**，不应使用 `{{}}` 包裹，而应直接写：
```
SetStringValue*TEMP#[$GlobalData:GenerateRareLvColorText=SUBARG$]
```
此时 `ResolveAllCommands` 阶段就会解析查询，`SetStringValue` 拿到的是已解析的值。

### 发现 2：`CheckConditionCallFuc` 的回调参数通过 `SendMessage` 会触发二次解析

`CheckConditionCallFuc` 通过 `SendMessage("SpePlotFuc", param)` 执行回调，会二次进入 `SpePlotFucPrefix`，其中 `ResolveAllCommands` 会解析 `[$null$]`。所以 `{{}}` 在此场景下实现的是**延迟求值**——条件为 True 时才解析回调参数中的查询指令。

### 发现 3：`{{}}` 的双重语义（需改造）

| 使用场景 | `{{}}` 的效果 | 是否合理 |
|---------|-------------|---------|
| 保护 `#` 不被分割 | `SplitRespectingBraces` + `StripBraces` | ✗ 职责耦合，应拆分给 `(())` |
| 延迟 `[$...$]` 求值 | `ResolveAllCommands` 不解析内部 | ✅ 这是 `{{}}` 唯一应有的职责 |
| 保护 SUBARG 不被替换 | ❌ 不支持，Step0 在 Step1 之前 | 需注意 |

## 10. 改造方案：`{{}}` 仅延迟求值，`(())` 仅保护分隔符

### 10.1 问题根源

当前 `{{}}` 同时承担两个职责：

1. **延迟求值**：保护内部 `[$查询$]`/`[&算术&]` 不被 `ResolveAllCommands` 解析
2. **分隔符保护**：保护内部 `#` 不被 `SplitRespectingBraces` 拆分

当 `{{}}` 内部**同时包含**查询指令和分隔符时，两者耦合导致矛盾：

```
SetStringValue*TEMP#{{[$GlobalData:GenerateRareLvColorText=SUBARG$]}}
                              ↓ StripBraces 剥离 {{}}
SetStringValue*TEMP#[$GlobalData:GenerateRareLvColorText=SUBARG$]
                              ↓ 直接传给 handler
value = "[$GlobalData:GenerateRareLvColorText=SUBARG$]"  ← 字面量，未被解析!
```

用户本意是"保护 `#` 不被拆分，但查询要立即解析"，但 `{{}}` 无法做到——它"保护了一切"。

### 10.2 为什么不采用向后兼容方案

**向后兼容方案**（`{{}}` 继续保护分隔符 + `(())` 新增）看似零迁移成本，但存在根本问题：

1. **场景 A 的 bug 未修复**：现有 `SetStringValue*TEMP#{{[$GlobalData:...$]}}` 的错误行为（存储字面量而非查询结果）**继续存在**，用户仍需手动改为 `(())` 才能修复
2. **语义不清**：`{{}}` = 延迟求值 + 分隔符保护（两个职责），`(())` = 仅分隔符保护（一个职责）。职责不对等
3. **"兼容"是假象**：让错误脚本继续以错误方式运行，不如让它明确报错

**方案 B 的迁移成本是一次性的**，且修改后语义永远清晰。

### 10.3 改造目标

| 保护符 | 职责 | 生效阶段 | 实现位置 |
|--------|------|----------|----------|
| `{{内容}}` | **仅延迟求值**：保护内部查询指令不被 `ResolveAllCommands` 解析；**不再保护**内部分隔符 | `ResolveAllCommands` | ConditionQueryHandlers |
| `((内容))` | **仅分隔符保护**：保护内部分隔符 `#`/`;`/`-` 不被拆分，**不阻止**查询指令解析 | 字符串拆分时 | CommonHandlers (ParseCommandParams 等) |

**核心原则**：每种语法只做一件事。需要两者时嵌套使用。

### 10.4 两种保护符的语义对比

| 维度 | `{{}}` 延迟求值保护符 | `(())` 分隔符保护符 |
|------|----------------------|---------------------|
| 查询指令 `[$...$]` | **不解析**（延迟到下游） | **照常解析**（立即求值） |
| 算术指令 `[&...&]` | **不解析** | **照常解析** |
| 分隔符 `#`/`;`/`-` | **照常拆分**（改造后不再保护） | **不拆分** |
| SUBARG 替换 | **不保护**（Step0 在保护前执行） | **不保护** |
| 剥离时机 | `ParseCommandParams` → `StripBraces` | `ParseCommandParams` → `StripParens` |
| 典型场景 | `CheckConditionCallFuc` 回调参数，条件为真时才求值 | 参数含 `#`/`;`/`-`，需作为整体传递 |

### 10.5 用例验证

#### 用例 1：立即求值 + 分隔符保护（当前 `{{}}` 无法解决的场景）

```
输入: SetStringValue*TEMP#(([$GlobalData:GenerateRareLvColorText=SUBARG$]))
```

| 阶段 | 处理 | 结果 |
|------|------|------|
| ResolveAllCommands | `(())` 不阻止查询解析 | `SetStringValue*TEMP#((红宝石))` |
| SplitRespectingBraces('#') | `(())` 保护 `#`（本例无内部 `#`） | `["TEMP", "((红宝石))"]` |
| StripParens | 剥离 `(())` | `["TEMP", "红宝石"]` |
| **SetStringValue** | | **key="TEMP", value="红宝石" ✓** |

对比改造前用 `{{}}`：value 会是字面量 `[$GlobalData:GenerateRareLvColorText=红宝石$]` ✗

#### 用例 2：仅保护分隔符（无查询指令）

```
输入: SomeFunc*((A#B))#C
```

| 阶段 | 处理 | 结果 |
|------|------|------|
| ResolveAllCommands | `(())` 内无查询语法 | 不变 |
| SplitRespectingBraces('#') | `(())` 保护第一个 `#` | `["SomeFunc*((A#B))", "C"]` |
| StripParens | 剥离 `(())` | `["SomeFunc*(A#B)", "C"]` |
| **handler** | | **第一个参数为 "A#B"，未被拆分 ✓** |

#### 用例 3：仅延迟求值（无分隔符冲突）

```
输入: SetStringValue*Key#{{$HeroData:Name:小白$}}
```

| 阶段 | 处理 | 结果 |
|------|------|------|
| ResolveAllCommands | `{{}}` 保护 `[$...$]` 不解析 | 不变 |
| SplitRespectingBraces('#') | `{{}}` **不再保护** `#` | `["Key", "{{$HeroData:Name:小白$}}"]` |
| StripBraces | 剥离 `{{}}` | `["Key", "$HeroData:Name:小白$"]` |
| **SetStringValue** | | **key="Key", value="$HeroData:Name:小白$" ← 延迟求值语义正确** |

> 注：此用例中 `{{}}` 内无 `#`，所以是否保护分隔符无差异。如果有 `#`，参见用例 4。

#### 用例 4：延迟求值 + 分隔符保护（嵌套使用）

改造前（错误写法，`{{}}` 同时承担两职责）：
```
CheckConditionCallFuc*expr#SpePlotFuc#{{SetStringValue*Key#[$null$]}}
```

改造后（正确写法，`(())` 保护 `#`，`{{}}` 延迟求值）：
```
CheckConditionCallFuc*expr#SpePlotFuc#(({{SetStringValue*Key#[$null$]}}))
```

| 阶段 | 处理 | 结果 |
|------|------|------|
| ResolveAllCommands | `(())` 不阻止解析；`{{}}` 保护 `[$null$]` 不解析 | 不变 |
| SplitRespectingBraces('#') | `(())` 保护 `#`；`{{}}` **不再保护** `#` | `["CheckConditionCallFuc*expr", "SpePlotFuc", "(({{SetStringValue*Key#[$null$]}}))"]` |
| StripParens + StripBraces | 先剥离 `(())`，再剥离 `{{}}` | `["CheckConditionCallFuc*expr", "SpePlotFuc", "SetStringValue*Key#[$null$]"]` |
| SendMessage 回调 | SpePlotFucPrefix → ResolveAllCommands | `[$null$]` → `""` |
| **SetStringValue** | | **key="Key", value="" ✓** |

#### 用例 5：反向嵌套（`{{}}` 在外，`(())` 在内）

```
输入: SomeFunc#{{A*((B#C))}}#D
```

| 阶段 | 处理 | 结果 |
|------|------|------|
| ResolveAllCommands | `{{}}` 保护一切 | 不变 |
| SplitRespectingBraces('#') | `{{}}` **不再保护** `#` → 第一个 `#` 会拆分 | `["SomeFunc", "{{A*((B#C))}}", "D"]` |

**⚠️ 此写法有问题**：`{{}}` 不再保护 `#`，导致 `#D` 被拆分为独立参数。正确写法应将 `(())` 放在外层：

```
输入: SomeFunc#(({{A*((B#C))}}))#D
```

| 阶段 | 处理 | 结果 |
|------|------|------|
| ResolveAllCommands | `{{}}` 保护查询不解析，`(())` 不影响 | 不变 |
| SplitRespectingBraces('#') | `(())` 保护 `#` | `["SomeFunc", "(({{A*((B#C))}}))", "D"]` |
| StripParens + StripBraces | | `["SomeFunc", "A*((B#C))", "D"]` |
| handler 内按 `#` 拆分 | `(())` 保护第二个 `#` | `["A", "((B#C))", "D"]` → `["A", "B#C", "D"]` |

**结论**：当需要同时延迟求值和保护分隔符时，`(())` 必须在外层，`{{}}` 必须在内层。

### 10.6 现有脚本迁移指南

#### 迁移规则

| 改造前 | 改造后 | 说明 |
|--------|--------|------|
| `{{不含查询指令的内容}}` | `((内容))` | 仅需分隔符保护 |
| `{{含查询指令但无#的内容}}` | `{{内容}}` | 仅需延迟求值，无需改 |

### 10.7 改造范围与分阶段实施

#### 第一阶段：`SplitRespectingBraces` 职责分离（最核心）

**修改文件**：`CommonHandlers.cs`

**1. `SplitRespectingBraces` 改造** — 移除 `{{}}` 的分隔符保护，新增 `(())` 的分隔符保护：

```csharp
public static string[] SplitRespectingBraces(string input, char separator)
{
    var parts = new List<string>();
    int parenDepth = 0;    // (()) — 唯一的分隔符保护符
    int start = 0;

    for (int i = 0; i < input.Length; i++)
    {
        if (i + 1 < input.Length && input[i] == '(' && input[i + 1] == '(')
        {
            parenDepth++;
            i++; // 跳过第二个 (
        }
        else if (i + 1 < input.Length && input[i] == ')' && input[i + 1] == ')')
        {
            parenDepth--;
            i++; // 跳过第二个 )
        }
        else if (input[i] == separator && parenDepth == 0)
        {
            parts.Add(input.Substring(start, i - start));
            start = i + 1;
        }
    }
    parts.Add(input.Substring(start));
    return parts.ToArray();
}
```

> **关键变更**：移除了对 `{{`/`}}` 的深度追踪。`{{}}` 不再保护分隔符。

**2. `StripParens` 新增** — 与 `StripBraces` 类似：

```csharp
public static string StripParens(string input)
{
    if (string.IsNullOrEmpty(input)) return input;
    if (input.StartsWith("((") && input.EndsWith("))") && input.Length > 4)
        return input.Substring(2, input.Length - 4);
    return input;
}
```

**3. `ParseCommandParams` 改造** — 统一剥离两种保护符：

```csharp
for (int i = 0; i < rawParams.Length; i++)
{
    rawParams[i] = StripBraces(StripParens(rawParams[i]));
}
```

**4. `ResolveAllCommands` 无需修改** — `(())` 不影响查询解析，正则 `\[\$(.+?)\$\]` 正常匹配 `(())` 内的 `[$...$]`。`{{}}` 的延迟求值行为不变。

**5. `ContainsParseableSyntax` 无需修改** — `(())` 本身不含查询语法，是否触发解析取决于 `[$`/`[&` 的存在。

#### 第二阶段：`ChangeNextPlotPatch` 中实现 `(())` 保护 `;` 和 `|`

**修改文件**：`PlotControllerChangeNextPlotPatch.cs`

将 `Split('|')` 和 `Split(';')` 改为使用 `SplitRespectingBraces`：

```csharp
// 原: string[] callBacks = clickCallFuc.Split('|');
string[] callBacks = CommonHandlers.SplitRespectingBraces(clickCallFuc, '|');

// 原: string[] parts = singleCallBack.Split(';');
string[] parts = CommonHandlers.SplitRespectingBraces(singleCallBack, ';');
```

并在 `SendMessage` 前剥离 `(())`：

```csharp
string methodArg = CommonHandlers.StripParens(parts[1]);
__instance.gameObject.SendMessage(parts[0], methodArg);
```

#### 第三阶段：各 handler 中实现 `(())` 保护 `-`（按需）

**涉及文件**：
- `ConditionQueryHandlers.cs`：5 处 `Split('-')`
- `PlotControllerSpePlotFucPatch.cs`：约 10 处 `Split('-')`

将 `.Split('-')` 改为 `CommonHandlers.SplitRespectingBraces(arg, '-')`，并在使用前调用 `StripParens`。

### 10.8 交叉嵌套规则

| 写法 | 是否允许 | 说明 |
|------|----------|------|
| `(({{abc}}))` | ✅ | 外层分隔符保护 + 内层延迟求值，**推荐写法** |
| `{{((abc))}}` | ⚠️ | 外层延迟求值，但 `{{}}` 不再保护 `#`，如内部含 `#` 会被拆分 |
| `((abc((def))ghi))` | ✗ | `(())` 不支持嵌套，深度 > 1 时行为未定义 |
| `{{abc{{def}}ghi}}` | ✗ | `{{}}` 不支持嵌套，深度 > 1 时行为未定义 |

**推荐嵌套顺序**：`(())` 在外，`{{}}` 在内。即 `(({{content}}))`。

原因：
1. `(())` 保护分隔符 → 防止 `#`/`;`/`-` 被拆分 → 在最外层确保整体性
2. `{{}}` 延迟求值 → 保护查询指令 → 在内层控制解析时机

### 10.9 `ResolveAllCommands` 对 `(())` 的处理

`(())` **不阻止** `ResolveAllCommands` 解析内部查询指令，因此无需特殊处理：

```
输入: A#((B#[$null$]))#C
ResolveAllCommands:
  Step 1: 保护 {{}} → 无 {{}}，不变
  Step 2: 解析 [$null$] → ""
  结果: A#((B#))#C        ← 查询已被解析，(()) 仍保留
```

`(())` 中的查询先被解析为值，然后 `(())` 保护值中的分隔符不被拆分。这正是"立即求值 + 分隔符保护"的语义。

### 10.11 风险评估

| # | 风险 | 等级 | 说明 |
|---|------|------|------|
| 1 | 现有 `{{}}` 含分隔符的脚本需迁移 | **中** | `{{A#B}}` → `(({{A#B}}))` 或 `((A#B))`，需逐一排查 |
| 2 | `((`/`))` 与自然文本冲突 | 极低 | 双括号 `(())` 在游戏数据中极少自然出现 |
| 3 | `(())` 内查询解析后含 `#`/`;`/`-` | **需关注** | 如 `[$GetStrVal:含#号$]` 解析为 `"A#B"`，`(())` 会保护此 `#`，这是期望行为 |
| 4 | `(())` 内 `(())` 嵌套 | 低 | 深度计数器不会崩溃，但剥离可能不符合预期 |
| 5 | `ResolveAllCommands` 对 `(())` 的误匹配 | **无** | `(())` 不含 `[$`/`[&`，正则不会误匹配 |
| 6 | 遗漏未迁移的 `{{}}` 含分隔符脚本 | **需关注** | 改造后 `{{}}` 不再保护分隔符，旧脚本中的 `{{A#B}}` 会被错误拆分 |
